The diagnosis, which is none of the plan's three guesses. The activation fires and focuses the panel: `audit/_probe2c98/focus-trace.mjs` (every `focus()` call with its stack, every focusin and focusout after the click) reads on `pnpm dev`, before the fix, `handleActivation` focusing the panel 76.5 ms after the click and react-focus-lock's `returnFocus` focusing the toggle 4 ms later from a microtask with no caller frame (`trace-current-dev-prefix.txt`). That return runs only in `handleStateChangeOnClient` when the trap leaves the trap list (`react-focus-lock@2.13.7`, `dist/es2015/Trap.js`, `lastTrap.returnFocus(!trap)`), and the trap is a `react-clientside-effect` class whose `componentWillUnmount` empties the list: React StrictMode's development-only simulated unmount and remount of a newly mounted component (`next@15.5.18`'s vendored React, `dist/compiled/react-dom/cjs/react-dom-client.development.js:16559-16579` (React `19.2.0-canary-0bdb9206-20250818`, the copy the app router runs; the same functions sit at `react-dom@19.2.6`'s `cjs/react-dom-client.development.js:18697-18717`), `doubleInvokeEffectsOnFiber` and `commitDoubleInvokeEffectsInDEV`, absent from the `react-dom-client.production.js` beside it) unmounts and remounts the trap once right after it activates; the deferred return then pulls focus off the panel, and the remounted trap recaptures the panel as its restore target. Next's app router turns StrictMode on by default (`next@15.5.18`, `dist/build/define-env.js:126-127`, `__NEXT_STRICT_MODE_APP` true when the config sets nothing), where legacy's pages router did not (`next@14.2.5`, the version `apps/gridkit/package.json:65` at `fce357d` pins, `dist/build/webpack/plugins/define-env-plugin.js:134-135`, the same two defaults, and `apps/gridkit/next.config.mjs` sets nothing). Why this shape. The predicate is react-focus-lock's own API (`returnFocus?: boolean | FocusOptions | ((returnTo: Element) => boolean | FocusOptions)`, `dist/cjs/interfaces.d.ts:14`, passed through by react-focus-on 3.10.2's `FocusOn`); a false answer leaves the trap's restore target in place (`Lock.js`, `originalFocusedElement` is nulled only when a return happens), so the remounted trap finds it set and the toggle stays the element Escape returns to. The ref is written in render because the unmounting trap calls the callback of the last render while the menu was open (the Lock renders with the trap gone in the same commit that flips the state, so no later render reaches it), and the trap unmounts in the commit's mutation phase, before a layout effect could write the ref; Chakra v2's `useLatestRef` wrote a ref the same way (`@chakra-ui/hooks@2.2.1`, the version `../node-modules/pnpm-lock.yaml` pins, `src/use-latest-ref.ts`: `ref.current = value` in render). Rejected: `reactStrictMode: false` in the site (hides every double-invoke bug to cover one library's, on no legacy line); deferring `handleActivation`'s focus past the return (a timer race, and the remounted trap would still recapture the panel, so Escape would return focus to a hidden panel); a code-free close of the item (production is right, but the gate and the ledger read `pnpm dev`, and the package is a library). The fix is in `NavHeader.tsx`, as the plan allowed.
