Legacy's `_app.tsx` wraps every page in `QueryParamProvider` from `use-query-params` with `next-query-params`'s adapter (difference `43c1babc2051`, regression on `shell`). The layout slice `a7bf623f885c` verified that the port's obvious translation does not hold: `next-query-params/app` (5.1.0) calls `useSearchParams()` in its adapter, so mounted in the root layout it fails `next build` on every static route (`useSearchParams() should be wrapped in a suspense boundary`), and wrapped in `Suspense` at the root it bails every route out to client-side rendering, the static HTML holding only `<template data-dgst="BAILOUT_TO_CLIENT_SIDE_RENDERING">` and no `<main>`. This slice closes that open unknown by Phase 0 (CLAUDE.md, Plans vs. reality): research and an adversarial review on Opus, the simplest design that survives, then the provider mounted once in the shell. Record `a78b167170b8`; decisions `ee86d68a`, `2032533f`.

Phase 0, closed by research in the sources and one adversarial review on Opus. The unknown: `next-query-params@5.1.0`'s app adapter calls `useSearchParams()` unconditionally (`dist/app.cjs.development.js:12`). Under a static prerender that hook throws `BailoutToCSRError` to the nearest Suspense boundary (`next@15.5.18` `client/components/navigation.js:107-112`, `bailout-to-client-rendering.js`). On the client it is a context read. The design that survived has three parts. The query is empty on the server and during hydration, by a `useSyncExternalStore` hydrated flag: the pages adapter's `router.isReady` two-part render (`next-query-params` `NextAdapterPages-293777d9.js:14-24`). Once hydrated, the query is the one Next's router holds, read by `useSearchParams()` behind a `typeof window` guard that is constant for each render tree, so a consumer mounted by a navigation reads its own URL on its first render, and back and forward follow the history. Writes are `window.history.pushState` and `replaceState`, which Next patches to keep `usePathname` and `useSearchParams` in sync (`app-router.js:290-334`): the app-router form of legacy's shallow `router.replace`. Dropped: the library adapter inside each consumer's client boundary (four providers where legacy had one, and writes become full `router.push` navigations); another library (nuqs defers its hook to the consumers, but its API is not `useQueryParams`, so the five route items would change shape again); `export const dynamic = 'force-static'` on the root layout with the library adapter (`bailoutToClientRendering` returns under `forceStatic`, but every URL with a query would then mismatch on hydration, and every future route is forced static); wrapping `window.history` to observe Next's own navigations (they carry `__NA` and skip the patch, and the patch is installed in an effect, so the order is not stable).

The reviews. The Phase 0 review found one defect, fixed before the code reviews: the first prototype reported the search from a child's layout effect, so a consumer mounted by a soft navigation first committed the previous URL's search (a MutationObserver probe: `chg: old->new`). The shipped adapter derives it in render (the probe: one insertion, `ins:new`). Its second finding, taken: the pure `hrefFor` helper's no-`?` branch was dead (`use-query-params` `updateSearchString.ts:96-98` always passes `''` or `?...`), so the helper and its Vitest seam went. The code reviews ran on Opus: Standards, Spec and Parity, then Spec and Standards again on the fix, then Spec a third time. Spec found one critical, twice. First: the adapter handed `use-query-params` a snapshot of the search, and the setter reads `adapter.location.search` at setter time (`useQueryParams.ts:152`) while Next's router update lands in a `startTransition` (`app-router.js:296-303`), so a second `setQuery` on another key in the same task merged onto the old search. The reviewers' fix, legacy's live `window.location`, would bring the soft-navigation defect back: the app router updates the URL at commit (`HistoryUpdater`, `app-router.js:95-116`), so a consumer's render during a navigation would read the old URL and nothing would re-render it. So the adapter keeps the writes ahead of the router in a ref, and its `location.search` getter returns the latest write. Second, on that fix: a single last-write ref cleared on any router report lost `other=y` when three writes ran in back-to-back tasks, since the router reported the first write while later ones were pending, and the setter reads through an adapter that `use-query-params` captures in a passive effect, a render or two old. Now the writes are a list, oldest first: a report of one of them drops the writes up to it, a report of none of them is a navigation and drops them all, and the getter reads the latest write or the latest report through refs, never a render's closure. Probed, three runs each: push, then two keys, then replace, in back-to-back tasks, ends at `?search=replaced&other=y`; two keys in one handler at `?search=x&other=y`; a write then back, a write then `router.push`, an external replace read later, all right. The third Spec round found no critical and one medium: a time-sliced render React throws away keeps its ref trim, so a write made while a heavy transition render is in flight can read the older search until it commits; not reproduced under 60x CPU throttling, and trimming at commit instead would make a consumer's first render on a soft navigation read the old URL, the Phase 0 defect. Kept, and recorded in [[1eddda919812]] beside the other gap against legacy's live location: a history write made outside the adapter followed by a `setQuery` in the same task reads the older search. No consumer reaches either. Taken too: the doc comment cut to one paragraph with the `Note(cc)` as its own line comment, and a comment naming the refs read and written in render as the deviation from React's advice it is; the line count dropped from the item; a log line on [[c94f539612d6]], whose Current names the closed item; the Done when's bailout letter noted on this plan's Log. Review findings dropped: none.

Proof. A throwaway route `app/probe-qp/` (not committed) drove `useQueryParams` under Playwright against `pnpm dev`. The server HTML for `/probe-qp?search=fromserver` carries an empty value and one `<main>`. The value fills after hydration. `pushIn` adds a history entry and `replaceIn` does not. Back, forward and `window.next.router.push` to the same path with a new search each update the value. No hydration warning in the console. The consumers, unchanged this slice, still work under the provider: `/designs?q=shelf` shows 3 cards and `/designs` 37, `/stories` lists 6 with its four filters, `/tools/cutting-planner` loads. Screenshot and DOM pairs were captured on `/`, `/about`, `/designs`, `/designs/bed-frame`, `/stories`, `/tools/cutting-planner` and `/contact` at three widths and looked at: no visual change, the shell being the only diff. No unit test: the adapter's pure edge went with the helper, and the seam is held by the probes above and the screenshot pairs.
