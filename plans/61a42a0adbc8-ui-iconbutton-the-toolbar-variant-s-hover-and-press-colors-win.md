## Outcome

Shipped in `../ui` at commit d736bfe on `main` over `9642114`, by pathspec (`src/components/Button.tsx`, `src/components/nav/NavHeader.tsx`, `CHANGELOG.md`), not pushed: the `toolbar` variant's rest color reads a CSS variable with a fallback, `color: 'var(--toolbar-color, {colors.gray.700})'`, and the toggle sets the variable in place of its `color` style prop, `css={{ '--toolbar-color': 'colors.gray.900' }}`. The mechanism, read in `@chakra-ui/react@3.35.0` (`dist/esm/styled-system/cva.js:46`, `layers.js`, `use-resolved-props.js:49`, `utility.js:120` and `:129`): a recipe's styles are wrapped in `@layer recipes` and a style prop or `css` value is emitted unlayered, so under Chakra v3 an unlayered `color` beats every layered state whatever its specificity, where under Chakra v2 the variant's nested selectors beat the `sx` color by specificity. A `--*` key's value resolves through `tokens.getVar` (`colors.gray.900` to `var(--chakra-colors-gray-900)`) and a `{colors.gray.700}` reference expands inside a value string, and `SystemStyleObject` admits a `--*` key, so the variable is set unlayered where it fights no state, and the rest, hover, press and focus colors are all the recipe's, cascading by specificity inside the layer as legacy's did. The emitted rules on `pnpm dev` show it: `.css-h29y5u { --toolbar-color: var(--chakra-colors-gray-900); ... }` unlayered, the three state colors inside the layer (`hover-rules-after.json`; the `hover-rules-before.json` beside it is the same dump on the published 1.2.0, the mechanism's proof, not the override before the edit). Resolving the `toolbar` variant through the package's own system (`recipe-resolve.mjs`, bundled with esbuild and run under node) prints the layered rest declaration `color: var(--toolbar-color, var(--chakra-colors-gray-700))` beside the three states and the toggle's `css` as `--toolbar-color: var(--chakra-colors-gray-900)` alone, so the one other `toolbar` consumer, the catalog's `Clear search` button on `/designs` (`app/_components/catalogue/Catalogue.tsx:408`, legacy's `search-bar.tsx:35-40`), which sets no variable, keeps `gray.700` at rest through the fallback; no probe read it on `pnpm dev`. The variable is the shape the package's `--accordion-padding-y` (the recipes slice) and Chakra's own `--focus-ring-width` use.

The candidates weighed. The toggle's color written with its states in `css` (a copy of the variant's three states on the consumer, drifting from the recipe); a second variant or a compound variant carrying `gray.900` at rest (a copy of the variant's block, or a new variant key, for one consumer); the recipe's states raised above the style prop (only `!important` or `disableLayers` on the system does that, the second changing every component's cascade); a `css={{ '@layer recipes': { color: 'gray.900' } }}` on the toggle (works, and relies on the layer's name and Emotion's at-rule nesting). The variable is the smallest change: one line in the recipe, one on the toggle, no other `toolbar` consumer touched, with the constraint in a comment on each. Legacy had two `toolbar` consumers setting `gray.900` this way (the toggle and the store's Cart, `apps/gridkit/components/layouts/main.tsx:102-107` at `fce357d`, not ported) and one bare (the catalog search's clear button); a consumer that wants legacy's `sx` color now sets the variable.
