## Outcome

The package version stays 1.2.0.

The mechanism, decided at Phase 0 and followed by the ui nav, brand footer, mdx and media, and LinkCard slices: one small framework context (`src/framework.tsx`: `FrameworkProps { usePathname?: () => string | null; linkComponent?: ElementType }`, `useFramework()` never throws, the defaults being no pathname and no link component). `NavContextProvider({ items, usePathname?, linkComponent? })` is the app's one wiring point and the only thing that fills it, legacy's shape (`NavContextProvider({ items, usePathname })` in `packages/ui-nav/src/context.ts`) plus the link component the private legacy packages hard-coded from `next/link`. A composite that renders its own anchors reads the context as its default: `NavBar` and `NavList` (`as={linkComponent}`, `isSelected` from `usePathname()`), `Footer`'s internal links, `MdxLink`'s route links, `LinkCard`'s overlay for a non-external href when no `linkComponent` prop is given. A leaf link component (`Link`, `LinkButton`, `LinkIconButton`) keeps the explicit `as`, the 1.2.0 idiom, since its caller holds the href and knows whether it is a route; a context default there would send `mailto:`, `#hash`, `https://` and `target="_blank"` links through the router link. `FrameworkProvider` is a module-internal component, not a package export. Images: `MediaProvider({ cloudinaryName?, imageComponent? })`, with `ImageComponentProps`, `ImageComponent`, `ImageLoader`, `ImageLoaderProps` and `StaticImageSource` declared in `src/components/media/types.ts` with `next/image`'s shapes (`next/image`, `next/link` and `usePathname` from `next/navigation` were checked assignable to the new types by a temporary site file under `tsc`); without an image component a raster `Image` renders a plain `<img>` on one URL at the numeric `width` or 1280, the image-only props dropped, `fill` as absolute positioning; a missing cloud name still throws.

Candidates at Phase 0, reviewed on one Opus sub-agent: (a) props everywhere failed at `MdxLink`, reached only through the static `mdxComponents` map, so it would have needed a factory or plain anchors; (b) the framework context, chosen in the cut-down form (private, filled by the nav provider only, no merging over a parent, leaves explicit); (c) a `@villagekit/ui/next` subpath rejected, since a `next` import would remain under `src/` and it layers a second API over (a) or (b). The review's other calls, all taken: a stable module-level `useNoPathname` as the default so the hook order never changes; the `<img>` fallback strips the image-only props; the missing cloud name keeps throwing.
